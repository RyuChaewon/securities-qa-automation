# ChatGPT 요청문

첨부된 파일은 1Q HTS 계좌정보 화면 0701~0725 중 등록된 14개 화면의 테스트 시나리오 생성용 근거다. 다음 파일을 모두 읽고 작업하라.

- `02_화면_시나리오_컨텍스트.json`: 화면별 MAP 컨트롤, 조회·상태·결과 관계, 검증 조건, 과거 런타임 관찰
- `03_공통_테스트데이터_사전.json`: 공식 선택지, 종목 마스터 표본, 오류코드, 공통 데이터 전략
- `04_데이터셋_작성_계약.json`: 현재 실행기가 받을 수 있는 변수 구조와 제한
- `05_생성결과.schema.json`: 반드시 만족해야 하는 최종 JSON Schema
- `06_생성결과_예시.json`: 형식 예시이며 범위나 값은 복사하지 말 것
- `07_오류_판정_정책.md`: 기대 검증과 제품 결함을 구분하는 기준

## 목표

각 대상 화면에 대해 기본 조회, 모든 유한 선택지, 날짜·텍스트 경계, MAP 입력 검증, 상태 토글로 나타나는 하위 요소, 조회·페이지·내보내기·연계 화면을 가능한 범위에서 커버하는 테스트 시나리오와 테스트 데이터를 생성하라.

## 필수 규칙

1. 최종 산출물은 `05_생성결과.schema.json`을 만족하는 UTF-8 `generated-scenarios.json` 파일이어야 한다. 채팅 본문에는 화면별 시나리오 수, 변수 수, 미해결 항목 수만 요약하라.
2. 화면번호는 컨텍스트에 등록된 14개만 사용한다. 0701~0725 사이의 미등록 번호를 지어내지 않는다.
3. 계좌번호, 예금주, 비밀번호, 비밀번호 환경변수 이름을 생성하거나 요구하거나 출력하지 않는다. 계좌는 로그인된 테스트 계좌의 화면 기본값을 사용한다.
4. MAP `definitionOrder`를 실제 탭 순서로 단정하지 않는다. 모든 시나리오의 `executionOrder`는 `RuntimeTabOrder`다.
5. MAP 논리 ID와 화면 표시문자가 모호하면 좌표·라벨을 발명하지 말고 `locatorRequests`와 `reviewItems`에 기록한다.
6. 공식 입력 선택지는 각 값을 빠짐없이 테스트 데이터에 넣는다. 라디오·체크·콤보·탭은 가능한 모든 상태를 포함한다.
7. 날짜 값은 `yyyyMMdd`를 사용하고 `generationSummary.referenceDate`를 기준으로 산정 근거를 적는다. 영업일 여부를 확정할 수 없으면 가정으로 명시한다.
8. 각 MAP `validationRules.ruleId`는 음성 테스트로 커버하거나 `coverageGaps`에 미생성 사유를 적는다. `ValidationRequired`에는 원문 기반 `messagePatterns` 또는 공식 `errorCodes`가 필요하다.
9. 의도한 잘못된 입력을 HTS가 거부하는 것은 정상 검증이다. 시스템·통신·인증·프로그램 실패는 어떤 허용 규칙으로도 숨기지 않는다.
10. 설치 자료에 없는 잔고·손익·정산 금액의 정답은 추측하지 않는다. 그런 결과는 표시·갱신·무응답·오류 신호만 관찰하고 `NeedsBusinessData` 또는 검토 항목으로 남긴다.
11. 조합 수가 작으면 전체 조합을 사용한다. 폭증하면 단일요인과 pairwise를 사용하되 생략한 조합과 이유를 명시한다.
12. 모든 actionable control은 하나 이상의 `coveredControls`에 나타나거나 화면의 `coverageGaps`에 이유가 있어야 한다.
13. 근거는 `sourceRefs`와 `expectedOutcome.evidence`에 화면번호, control logicalName, validation ruleId, 설치 사전 ID 중 하나 이상으로 기록한다.

생성을 시작하기 전에 내부적으로 스키마와 14개 화면 목록을 검증하고, 완성 후 다시 JSON Schema 적합성과 컨트롤·검증 규칙 커버리지를 자체 점검하라.
